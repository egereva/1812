# 1812 — руководство по редактированию контента

## Быстрый старт: как исправить текст за 5 минут

Этот раздел рассчитан на компьютер, где проект уже скачан и рабочее окружение настроено. Если папки проекта нет или команды проверки не запускаются, обратитесь к руководителю проекта. Устанавливать программы и настраивать публикацию для простой правки текста не нужно.

1. Откройте Visual Studio Code (VS Code). Выберите **Файл → Открыть папку** и укажите папку `1812`. Открывайте всю папку, а не отдельный файл.
2. В левой панели найдите папку **content**. Если панели нет, выберите **Вид → Проводник**.
3. Откройте **ru** для русского текста или **en** для английского. Например, `content/ru/dictionary.json` — русский словарь.
4. Нажмите **Ctrl+F** (на Mac **⌘F**) и найдите `"id": "berezina"`. Это статья «Березина», доступная локально по адресу `/dictionary/berezina`.
5. Найдите внутри этой записи нужное поле. Сейчас там написано:

   ```json
   {
     "title": "Березина",
     "shortDescription": "Ключевой эпизод отступления Великой армии в ноябре 1812 года."
   }
   ```

   Здесь показан **фрагмент записи**, а не весь файл. Исправляйте только текст **внутри кавычек справа от двоеточия**. Имена `title` и `shortDescription`, скобки и запятые оставьте на месте. В приведённом заголовке опечатки нет: менять его ради упражнения не нужно. Если вы случайно написали «Березинна», исправьте на «Березина».

6. Сохраните файл: **Ctrl+S** / **⌘S**. Чтобы отменить случайное изменение, нажмите **Ctrl+Z** / **⌘Z**. Найдите ту же запись в `content/en/dictionary.json`: проверьте, нужен ли соответствующий перевод правки.
7. Посмотрите на красные подчёркивания и откройте **Вид → Проблемы**. Ошибок JSON быть не должно. Затем выполните проверки из раздела «Как проверить изменения». Отсутствие красных подчёркиваний не доказывает, что все связи и исторические сведения верны.
8. Сохранение меняет **локальный файл на вашем компьютере**. Опубликованный сайт пока не обновился. Проверить результат можно локально; для GitHub Pages нужна проверенная новая сборка и публикация через существующий workflow. Передайте правку руководителю проекта.

Для изменения исторического смысла сначала подготовьте источник и согласуйте текст с учителем. Даже настоящую опечатку нужно отличать от старого написания фамилии или исторического названия.

## 1. Как устроены данные

В каждой языковой папке находятся пять файлов:

| Файл              | Что хранит                                                        | Где искать результат                                             |
| ----------------- | ----------------------------------------------------------------- | ---------------------------------------------------------------- |
| `site.json`       | Название и описание проекта, введение главной, тексты «О проекте» | Главная и `/about`                                               |
| `places.json`     | Исторические места и места памяти                                 | `/map`, `/places/…`, preview карты на главной                    |
| `timeline.json`   | События войны                                                     | `/timeline`, `/timeline/…`; выбранные события на главной         |
| `dictionary.json` | Люди, термины, события, места и произведения                      | `/dictionary`, `/dictionary/…`; выбранные статьи на главной      |
| `sources.json`    | Источники исторических сведений и происхождение изображений       | `/sources`, ссылки на источники в материалах и под изображениями |

Английские страницы имеют начало `/en/`. На опубликованном сайте перед маршрутом добавляется `/1812/`: например, `https://egereva.github.io/1812/en/dictionary/berezina`. **Не вписывайте `/1812/` в slug или пути изображений в JSON**: приложение добавляет его само.

В `site.json` находится один объект `{…}`. В остальных четырёх файлах — массив записей `[…]`. Сейчас в каждом языке 13 мест, 20 событий, 29 статей и 68 источников. Это утверждённый набор; тесты специально защищают его от случайных изменений.

Короткие подписи интерфейса, например названия кнопок, находятся отдельно в `i18n/locales/ru.json` и `en.json`. Hero-картины, некоторые короткие названия и подборки главной заданы в коде. Не пытайтесь добавить такие настройки в `site.json`: неизвестное поле не подключит новую функцию.

## 2. Что такое JSON

JSON — способ записать данные по понятным правилам. Он похож на анкету: слева название поля, справа значение.

```json
{
  "id": "borodino",
  "title": "Бородинское сражение",
  "featured": true,
  "sourceIds": ["src-bre-war", "src-cbr-borodino"]
}
```

Это сокращённый фрагмент существующего события, не готовая новая запись.

- **Объект `{}`** — одна анкета, например одно событие. Его поля разделены запятыми.
- **Массив `[]`** — список. Это могут быть записи, абзацы или ID источников. `[]` означает пустой список.
- **Строка** — текст в двойных кавычках: `"Березина"`. Названия полей тоже пишут в двойных кавычках.
- **Число** — без кавычек: `55.73972`. В JSON десятичная часть отделяется точкой, не запятой.
- **`true` / `false`** — «да» / «нет», без кавычек. Например, у события поле `featured` задаёт выделение в хронологии. `"true"` — уже текст, а не ответ «да».
- **`id`** — постоянный ключ записи. По нему другие материалы находят её. Не переводится и не меняется при исправлении заголовка.
- **`slug`** — часть адреса страницы. У места `kutuzov-hut` получается `/places/kutuzov-hut`. Существующие slug сохраняйте; для новых используйте понятные латинские слова с дефисами без пробелов, например по образцу существующих записей.
- **Связь** — ID другой записи в специальном списке. `sourceIds: ["src-bre-war"]` ссылается на источник из `sources.json`. Название источника вместо ID не подойдёт.

### Типичные ошибки

Ниже специально показан неправильный текст. В рабочие файлы его не копируйте.

```text
{ "title": "Березина }            ← нет закрывающей кавычки
{ "title": "Березина", }          ← лишняя запятая перед }
[ "src-bre-war" }                 ← открыли [, а закрыли }
{ "title": "Березина" "id": "berezina" }  ← нет запятой между полями
```

Правильно:

```json
{ "title": "Березина", "id": "berezina" }
```

Между элементами нужна запятая, **после последнего — нет**. Нельзя вставлять комментарии `//` и `/* … */`. Для кавычек внутри строки удобны русские «ёлочки»; двойную прямую кавычку нужно записывать как `\"`. Новый абзац в статье — новая строка массива `content`, а не клавиша Enter посреди строки. Не вставляйте HTML (`<p>…</p>`) или Markdown (`**жирный**`): абзацы материалов отображаются обычным текстом.

## 3. Справочник полей

В таблицах **«Да»** означает обязательное поле. **«Нет»** — его можно не включать, если данных нет. Не заменяйте отсутствующее поле пустой строкой или `null`. Обязательные тексты и источники должны быть заполнены.

«Текст» в последней колонке означает: можно исправлять язык, сохраняя смысл; новые исторические сведения требуют проверки по источникам. «С проверкой» означает редакционную и техническую проверку. «С разработчиком» — не менять самостоятельно. Все примеры ниже взяты из существующих материалов; отдельные значения показывают форму, а не целый JSON-файл.

### 3.1. `site.json`: главная и «О проекте»

Это объект, вложенные поля которого удобно искать по их имени. Запись `about.sections[].title` ниже означает: `title` внутри **каждого элемента** списка `sections` внутри `about`; символы `[]` не нужно добавлять в имя поля.

### 3.2. `places.json`: места

Образцы: `kutuzov-hut` («Кутузовская изба»), `intercession-church-fili` («Церковь Покрова в Филях»). Текст используется на странице места и в карточке карты. Медиа необязательны: место без проверенного изображения остаётся полноценным материалом.

У `historicalStatus` перечень **закрытый**:

| Значение            | Что означает                                    | Слой карты |
| ------------------- | ----------------------------------------------- | ---------- |
| `event-site`        | Место исторического события                     | 1812       |
| `surviving-witness` | Сохранившийся объект, существовавший в ту эпоху | 1812       |
| `lost-site`         | Утраченное место или объект                     | 1812       |
| `reconstruction`    | Более позднее воссоздание                       | Память     |
| `memorial`          | Поздний памятник                                | Память     |
| `museum`            | Музей                                           | Память     |

Например, у Кутузовской избы **категория** `museum`, но **исторический статус** `reconstruction`. Это разные поля. Не присваивайте реконструкции статус подлинного здания ради другого цвета маркера.

`exact` означает точную привязку; `approximate` — приблизительный ориентир. Для утраченного места может не быть современного адреса. Для непроверенного изображения не нужно придумывать путь: отсутствие `coverImage` допустимо. Сейчас четыре места имеют пары сравнения: `kuntsevo-estate`, `borodino-panorama-museum`, `intercession-church-fili`, `triumphal-arch`; у Кутузовской избы такой пары нет.

### 3.3. `timeline.json`: события

Образцы: `borodino` («Бородинское сражение») и `berezina` («Переправа через Березину»). У Березины есть даты начала и конца; у однодневного события конечная дата не нужна.

| `slug`                 | Часть адреса `/timeline/…`                      | `borodino`                                              | Да                                        | Существующий — с разработчиком                                    |

| `shortDescription`     | Краткое описание                                | Начинается с «Генеральное сражение у Бородина…»         | Да                                        | Текст, учитывая защитные тесты                                    |
| `content`              | Массив абзацев статьи                           | Сейчас три абзаца у каждого события                     | Да                                        | Текст; изменения защищены тестами                                 |

| `dateEndOldStyle`      | Конец многодневного события по старому стилю    | У Березины `1812-11-16`                                 | Нет                                       | Только по источнику                                               |
| `dateEndNewStyle`      | Конец по новому стилю                           | У Березины `1812-11-28`                                 | Нет                                       | Только по источнику                                               |
| `sortDate`             | Отдельный ключ хронологического порядка         | У `borodino` реально `1812-08-26`                       | Да                                        | С проверкой существующего порядка; не менять при текстовой правке |
| `image`                | Изображение detail-страницы, объект медиа       | `/images/timeline/borodino-hess-1843.jpg` в `image.src` | Нет                                       | С проверкой файла, прав и тестов                                  |
| `featured`             | Выделение обычного события в списке             | `true` или `false`                                      | Нет по модели; сейчас есть у всех         | С проверкой отображения и тестов                                  |
| `relatedPlaceIds`      | Места события, список ID                        | `borodino-panorama-museum` внутри списка                | Нет                                       | С проверкой                                                       |
| `relatedDictionaryIds` | Словарные статьи, список ID                     | `borodino-battle` внутри списка                         | Нет                                       | С проверкой                                                       |
| `relatedTimelineIds`   | Другие связанные события, список ID             | Сейчас это поле в файлах не заполнено                   | Нет, поддерживается моделью и связями     | С проверкой                                                       |
| `seo`                  | Объект метаданных                               | Сейчас отсутствует                                      | Нет                                       | См. таблицу SEO                                                   |

Даты — **строки** вида `"1812-09-07"`, месяц и день записывают двумя цифрами. Программа не вычисляет новый стиль и конечные даты за редактора. `sortDate` тоже не вычисляется: события сортируются по нему, а при совпадении — по ID. Не считайте его автоматически датой нового стиля: в реальном наборе у Бородина он совпадает со старым стилем. Для нового события согласуйте ключ с руководителем, сохраняя правильное место в существующей хронологии.

`featured` не добавляет событие на главную. Главная использует отдельную подборку из кода. Крупные опорные события Timeline тоже выбраны в `app/data/timelinePresentation.ts`. `image` события подключает изображение detail-страницы; некоторые изображения **списка** Timeline берутся из словаря по отдельному сопоставлению в коде.

### 3.4. `dictionary.json`: словарь

Образец — `berezina`. `letter` задаёт группу в алфавитном списке: `Б` на русском и `B` на английском. У разных языков первая буква заголовка может различаться.

| Поле                   | Что означает                            | Пример                                                          | Обязательное? | Можно менять?                                 |
| ---------------------- | --------------------------------------- | --------------------------------------------------------------- | ------------- | --------------------------------------------- |
| `id`                   | Ключ статьи                             | `berezina`                                                      | Да            | Существующий — с разработчиком                |
| `slug`                 | Часть адреса `/dictionary/…`            | `berezina`                                                      | Да            | Существующий — с разработчиком                |
| `title`                | Название                                | `Березина`                                                      | Да            | Текст                                         |
| `shortDescription`     | Краткое объяснение                      | `Ключевой эпизод отступления Великой армии в ноябре 1812 года.` | Да            | Текст                                         |
| `content`              | Массив абзацев                          | Три абзаца у `berezina`                                         | Да            | Текст; число абзацев защищено тестами         |
| `sourceIds`            | Массив ID источников                    | `["src-bre-war"]`                                               | Да, непустой  | С проверкой                                   |
| `letter`               | Буква алфавитной группы на данном языке | `Б` / `B`                                                       | Да            | С проверкой после изменения названия          |
| `category`             | Тип статьи                              | `event`                                                         | Да            | С проверкой; это не новый фильтр интерфейса   |
| `image`                | Объект изображения                      | `/images/dictionary/berezina-hess.jpg` в `image.src`            | Нет           | С проверкой; отсутствие изображения допустимо |
| `relatedPlaceIds`      | Связанные места                         | У `berezina` сейчас `[]`                                        | Нет           | С проверкой                                   |
| `relatedDictionaryIds` | Другие статьи словаря                   | У `berezina` сейчас `[]`                                        | Нет           | С проверкой                                   |
| `relatedTimelineIds`   | Связанные события                       | У `berezina` сейчас `[]`                                        | Нет           | С проверкой                                   |
| `seo`                  | Объект метаданных                       | Сейчас отсутствует                                              | Нет           | См. таблицу SEO                               |

В текущем словаре категории `person` (человек), `place` (место), `event` (событие), `monument` (памятник), `term` (понятие), `artwork` (произведение). Модель допускает строку, а не только этот список, но новые категории лучше согласовать. Буква переводится по заголовку; техническое значение категории остаётся одинаковым RU/EN.

### 3.5. `sources.json`: источники

Источники не имеют `slug`, отдельных detail-страниц, `content` или `sourceIds`. Их постоянный `id` используют другие записи. Каталог разделяет `type: "media"` и все остальные источники, сохраняя порядок записей внутри этих двух групп.

| Поле         | Что означает                                           | Пример                                                   | Обязательное?                                                 | Можно менять?                                  |
| ------------ | ------------------------------------------------------ | -------------------------------------------------------- | ------------------------------------------------------------- | ---------------------------------------------- |
| `id`         | Ключ источника                                         | `src-bre-war`                                            | Да                                                            | Существующий — с разработчиком                 |
| `title`      | Название источника                                     | `Отечественная война 1812`                               | Да                                                            | Исправлять по оригиналу                        |
| `type`       | Вид источника; `media` отдельно группирует изображения | `encyclopedia`                                           | Да                                                            | С проверкой; одинаково RU/EN                   |
| `author`     | Автор, если известен                                   | В media-записях есть авторы изображений                  | Нет                                                           | По оригиналу, без догадок                      |
| `publisher`  | Организация, издатель или площадка                     | `Большая российская энциклопедия`                        | Нет по модели; сейчас есть у всех                             | По оригиналу; также используется в attribution |
| `year`       | Год издания/создания, число                            | `1888` у `src-media-place-intercession-church-fili-1888` | Нет                                                           | По источнику, без кавычек                      |
| `url`        | Адрес источника, не адрес изображения на сайте         | `https://bigenc.ru/c/otechestvennaia-voina-1812-30a318`  | Нет по модели; текущие тесты требуют HTTPS URL у всех записей | По проверенному адресу; одинаково RU/EN        |
| `accessedAt` | Дата, когда редактор обращался к источнику             | `2026-09-25`                                             | Нет                                                           | Фактическая дата `YYYY-MM-DD`, одинаково RU/EN |

Сейчас используются `encyclopedia`, `library`, `museum`, `official-document`, `official-publication`, `official-reference`, `media`. Это существующие значения, а не закрытое перечисление модели. `media` — особое значение для каталога происхождения изображений. Если год или автор неизвестен, не придумывайте их. Не удаляйте запись только потому, что её URL совпадает с URL другого источника: разные записи могут ссылаться на один документ.

### 3.6. Объект изображения: все вложенные поля

Одинаковая форма используется у `image` статьи/события, `coverImage`, элементов `gallery`, а также `before` и `after` в паре сравнения.

| Поле          | Что означает                                         | Пример                                                                 | Обязательное?                                                          | Можно менять?                                 |
| ------------- | ---------------------------------------------------- | ---------------------------------------------------------------------- | ---------------------------------------------------------------------- | --------------------------------------------- |
| `src`         | Локальный путь к файлу                               | `/images/dictionary/berezina-hess.jpg`                                 | Да                                                                     | С проверкой файла и каталога доставки         |
| `alt`         | Описание изображения для людей, которые его не видят | `Художественное изображение переправы армии Наполеона через Березину.` | Да                                                                     | Текст, описывающий само изображение           |
| `caption`     | Подпись под изображением                             | `Петер фон Гесс. Переправа через Березину 17 (29) ноября 1812 года.`   | Нет по типу; для текущих иллюстрированных материалов требуется тестами | По источнику                                  |
| `description` | Дополнительное пояснение к подписи                   | `Позднейшее художественное изображение.`                               | Нет                                                                    | Текст; не терять различие картины и документа |
| `credit`      | Авторство и права                                    | `Петер фон Гесс · Общественное достояние / PD-Art`                     | Нет по типу; требуется для текущих медиа и пар                         | По проверенным сведениям                      |
| `sourceId`    | ID отдельного источника изображения                  | `src-media-berezina-hess`                                              | Нет по типу; требуется для текущих медиа и пар                         | С проверкой наличия в обоих `sources.json`    |

`caption` и `description` объединяются в видимую подпись. Автор из `credit` может не повторяться на экране, если он уже указан в подписи. Название площадки и ссылка берутся из соответствующей записи `sources.json`. Отсутствующие год, авторство и лицензию приложение не придумывает. Правильный `alt` и видимая подпись нужны отдельно.

### 3.7. Пара `beforeAfter`: все поля

| Поле             | Что означает                                         | Пример из пары храма                                    | Обязательное?                                                         | Можно менять?                             |
| ---------------- | ---------------------------------------------------- | ------------------------------------------------------- | --------------------------------------------------------------------- | ----------------------------------------- |
| `id`             | Постоянный ключ пары                                 | `intercession-church-fili-1888-2019`                    | Да                                                                    | С проверкой; одинаково RU/EN              |

| `caption`        | Общее пояснение сравнения                            | Пояснение о сохранившемся храме в разные годы           | Нет                                                                   | Текст                                     |
| `beforeDate`     | Подпись времени раннего изображения, строка          | `1888`                                                  | Необязательна в типе, но **обязательна в действующем валидаторе пар** | По источнику, переводить при наличии слов |

`beforeDate`/`afterDate` — подписи для читателя, а не даты события Timeline. В обоих изображениях пары валидатор требует локальный `/images/…`, непустой alt и credit, существующий sourceId. Показывайте одно и то же место в разные годы; не выдавайте позднюю картину за документальный снимок 1812 года.

### 3.8. Необязательный `seo`

SEO — сведения о странице для поисковой системы. Объект допускается у места, события и словарной статьи. Сейчас ни одна из этих записей не содержит `seo`.

| Поле              | Что означает                              | Пример / поведение                                 | Обязательное? | Можно менять?                                       |
| ----------------- | ----------------------------------------- | -------------------------------------------------- | ------------- | --------------------------------------------------- |
| `seo.title`       | Другой заголовок для метаданных           | Без него используется `title`, например `Березина` | Нет           | С проверкой; не меняет видимый H1                   |
| `seo.description` | Описание для метаданных                   | Без него используется `shortDescription`           | Нет           | С проверкой                                         |
| `seo.image`       | Поле пути изображения, объявленное в типе | В текущем коде вывода SEO **не подключено**        | Нет           | Не добавлять ради social preview; нужен разработчик |

Не добавляйте сюда `canonical`, `hreflang`, `baseURL` или API-ключ: таких полей у редакционных записей нет. Адреса и языковые метаданные формируются приложением.

## 4. Практические действия

### 4.1. Исправить опечатку

1. Найдите запись по ID, например словарную `berezina`.
2. Исправьте найденную опечатку внутри `title`, `shortDescription` или одной строки `content`. Не меняйте ID/slug и не создавайте второй объект.
3. Проверьте соответствующую запись EN, сохраните и выполните проверки. Правка пунктуации RU не всегда требует изменения английской фразы, но смысл должен совпадать.

### 4.2. Изменить краткое описание

1. У места `kutuzov-hut` найдите `shortDescription`: сейчас это «Музейное здание 1887 года на месте избы Военного совета» с точкой в конце.
2. Подготовьте короткий понятный текст по существующим источникам. Сохраните уточнение о позднем здании; нельзя превратить описание реконструкции в описание подлинной избы 1812 года.
3. Обновите английский вариант. Проверьте вступление страницы `/places/kutuzov-hut` и карточку на карте. Если запись когда-нибудь получит `seo.description`, его тоже нужно согласовать: тогда поисковое описание не будет автоматически брать `shortDescription`.

### 4.3. Добавить абзац

1. Подготовьте и согласуйте новый текст по источнику. Найдите массив `content` нужной записи.
2. Перед закрывающей `]` добавьте ещё одну строку в двойных кавычках; после прежнего последнего абзаца поставьте запятую, после нового последнего — нет.
3. Добавьте соответствующий абзац EN, проверьте `sourceIds`. Это операция со структурой текста, а не просто правка слова.

Форма массива на двух существующих абзацах словарной статьи `berezina`:

```json
[
  "Переправа через Березину стала одним из наиболее драматичных эпизодов отступления Великой армии из России. К концу ноября 1812 года войска Наполеона, уже понёсшие огромные потери, стремились перейти реку и избежать окружения русскими армиями.",
  "Основная переправа проходила 14–16 (26–28) ноября у деревни Студёнка. Французские сапёры навели мосты, по которым переправлялись боевые части, обозы и многочисленные отставшие. На обоих берегах шли тяжёлые бои, а скопление людей и транспорта усиливало хаос."
]
```

Это только иллюстрация синтаксиса: **у настоящей статьи есть ещё третий абзац, его не удаляйте**. Тесты сейчас фиксируют 95 абзацев словаря и по три абзаца каждого события. Добавление абзаца требует согласованного обновления проверок разработчиком. Для Timeline тесты защищают даже точный текст абзацев; подробнее ниже.

### 4.4. Добавить новый термин в словарь

1. Сначала подготовьте название, краткое описание, абзацы и источники на двух языках. Проверьте, что такого термина ещё нет.
2. Возьмите **структуру** существующего объекта `berezina` в `dictionary.json`: выделите весь объект от его `{` до соответствующей `}`. Внутри могут быть собственные вложенные скобки изображения — не обрывайте запись на них.
3. Создайте отдельный объект внутри общего массива. Между старым последним объектом и новым нужна запятая. Назначьте новые уникальные ID и slug; заполните собственный проверенный материал, `letter`, `category`, источники и связи. Не оставляйте чужие тексты или изображения «для примера».
4. В `en/dictionary.json` добавьте запись с теми же ID/slug и структурными связями, переводом и английской буквой. Изображение необязательно: для неиллюстрированной записи удалите целое поле `image` вместе с относящейся к нему запятой, а не только значение `src`.
5. Передайте обе записи руководителю и разработчику для проверки нового состава. Существующий генератор маршрутов включает dictionary-записи в detail routes; после успешной сборки и публикации получится новая страница. Однако тесты сейчас фиксируют 29 статей и media manifest, поэтому одного вставленного объекта недостаточно для завершения всей работы. На главную статья автоматически не добавится.

### 4.5. Добавить историческое событие

1. Возьмите объект `borodino` как образец структуры; для диапазона дат смотрите `berezina` в **timeline**, а не одноимённую словарную статью.
2. Подготовьте новый уникальный ID/slug, проверенные даты, согласованный `sortDate`, три абзаца, краткое описание и `sourceIds`. Не копируйте даты Бородина в новое событие.
3. Заполните связи. `featured` оставляйте `false`, если выделение не согласовано; значение должно совпасть EN. Не добавляйте конечные даты к однодневному событию без причины.
4. Создайте перевод в EN с теми же датами и ID. Даты уже являются строками, их не переводят в «26 августа» внутри технических полей.
5. Передайте на проверку: маршруты detail формируются из записей, но 20 событий, даты, связи и тексты защищены тестами. Новый опорный блок или включение события на главную потребуют отдельной настройки в коде.

### 4.6. Добавить место на карту

1. Подготовьте описание, источники и проверенную точку. По структуре можно ориентироваться на `kutuzov-hut`; для приблизительной привязки — на `fili-village`.
2. Создайте объект с новым ID/slug, `title`, `shortDescription`, непустыми `content` и `sourceIds`, `coordinates`, `category`, `historicalStatus`, `locationPrecision`. Координаты перепишите как числа: сначала проверьте, какое число широта, а какое долгота.
3. Для приблизительной привязки подготовьте `locationNote`. Если объект поздний или утрачен, не маскируйте это точной отметкой или неверным историческим статусом. Добавьте адрес и медиа только при наличии подтверждённых данных.
4. Создайте EN-запись с той же точкой, статусом, точностью и связями. Проверьте страницу места и слой карты, в который оно попадает.
5. Полная карта и preview получают каталог мест; детальные маршруты формируются из записей. Но тесты фиксируют 13 мест и их распределение по слоям, поэтому новый состав проверяет разработчик. Близкие точки могут объединяться в группу: новый материал не обязательно даст отдельную видимую кнопку в исходном масштабе. Проверьте раскрытие группы, карточку и переход к странице. Работа живой карты зависит от уже настроенного API; школьник не меняет его ключ.

### 4.7. Добавить источник

1. Найдите оригинал и выпишите его реальные сведения. Для структуры интернет-источника можно посмотреть `src-bre-war`:

   ```json
   {
     "id": "src-bre-war",
     "title": "Отечественная война 1812",
     "type": "encyclopedia",
     "publisher": "Большая российская энциклопедия",
     "url": "https://bigenc.ru/c/otechestvennaia-voina-1812-30a318",
     "accessedAt": "2026-09-25"
   }
   ```

   Это уже существующий источник: **не вставляйте его второй раз**. Для нового нужен новый уникальный ID и собственные реальные сведения.

2. Добавьте объект в RU и EN `sources.json`; ID, type, URL и дата обращения совпадают. Переведите название и библиографические подписи, не выдумывая автора или издателя.
3. Для книги используйте известные author/publisher/year. В текущем проекте тесты требуют HTTPS-ссылку и publisher у всех источников: для нового печатного источника без URL сначала согласуйте поддержку такого случая с разработчиком.
4. Для происхождения изображения выберите `type: "media"`, для исторического материала — подходящий другой type. Затем укажите новый ID в статье: в `sourceIds` для фактов или в `sourceId` объекта изображения для его происхождения.
5. Изменение количества 68 источников и двух групп потребует проверки тестов. Дата обращения — день вашей фактической проверки, а не автоматически скопированная дата образца.

### 4.8. Связать материалы

Настоящий пример из места `kutuzov-hut`, сокращённый до части связей:

```json
{
  "relatedDictionaryIds": ["kutuzov", "military-council-fili", "fili"],
  "relatedTimelineIds": ["council-fili"],
  "sourceIds": [
    "src-panorama-hut",
    "src-panorama-history",
    "src-mos-atlas",
    "src-prlib-fili"
  ]
}
```

1. Найдите целевую запись и скопируйте её **ID**. Например, у события Совета в Филях ID `council-fili`, у словарной статьи о нём — `military-council-fili`.
2. Добавьте ID в подходящий массив, соблюдая запятые. В `relatedPlaceIds` идут только места, в `relatedDictionaryIds` — статьи, в `relatedTimelineIds` — события. Пустой список `[]` допустим; `sourceIds` пустым быть не должен.
3. Повторите те же списки в EN в том же порядке. Не добавляйте связь записи с самой собой и не дублируйте один ID в списке.
4. Слой данных учитывает прямые и обратные связи: если место ссылается на статью, статья может показать это место и без повторения связи в своём JSON. Не нужно механически копировать все обратные списки. Источники подключаются через `sourceIds`, а не как отдельная историческая статья.
5. Проверьте раздел связанных материалов на обоих концах. Некоторые утверждённые связи закреплены тестами: при изменении состава потребуется их пересмотр с разработчиком.

### 4.9. Добавить или заменить изображение

1. Сначала проверьте происхождение, автора и разрешение на использование. Ссылка на страницу Wikimedia не является ни локальным файлом, ни автоматическим разрешением. Для собственного фото запишите авторство; проверьте, что подпись соответствует объекту и времени снимка.
2. Сохраните проверенный файл в подходящей папке `public/images/`. Существующие примеры: `dictionary/berezina-hess.jpg`, `places/intercession-church-fili-2019.jpg`, `timeline/borodino-hess-1843.jpg`. Не используйте путь существующей картины для другого события только ради заполнения пустого блока.
3. В JSON укажите путь **без `public`**, например `/images/dictionary/berezina-hess.jpg`, а не URL Wikimedia и не `/1812/images/…`. Проверьте точный регистр букв и расширение; на GitHub Pages они важны.
4. Заполните alt, caption, credit, при необходимости description и существующий media sourceId. Создайте или обновите соответствующий источник RU/EN. Оба языка используют один файл и sourceId, но свои alt и подписи.
5. Для cover/image заменяйте согласованный медиа-объект; для gallery добавляйте объект внутрь массива; для сравнения заполните обе стороны и даты из таблицы пар. Без подтверждённой картинки оставьте необязательное поле отсутствующим.
6. Передайте оригинал и сведения разработчику. Текущая доставка изображений использует `app/data/imageDelivery.json` и подготовленные копии в `public/images/delivery/`. Тесты проверяют размеры, состав и контрольные суммы — «отпечатки» файлов. Замена старого файла тем же именем всё равно требует обновления каталога и проверок. В сборке эти копии автоматически не создаются.

Без записи в каталоге helper умеет вывести существующий оригинал, но это **не означает**, что новый материал соответствует всем текущим тестам и требованиям к размеру файла. Команда `npm run media:prepare` существует, однако использует PowerShell и `System.Drawing`, то есть нынешний обработчик предназначен для Windows. На Mac не запускайте её как универсальный способ подготовки: поручите разработчику проверенную обработку медиа. Hero и изображения некоторых preview подключены отдельно из кода; изменение `image` статьи не заменяет все связанные изображения сайта.

### 4.10. Подготовить английскую версию

1. Найдите соответствующий файл в `content/en/`. Запись ищите по тому же ID, а не по русскому заголовку.
2. Переведите title, shortDescription, content, адреса и пояснения, alt/caption/description/credit, тексты SEO и библиографические подписи. Названия организаций и авторов оформляйте по проверенному принятому написанию.
3. Оставьте одинаковыми ID, slug, category, historicalStatus, locationPrecision, coordinates, sourceIds и списки связей, даты события и featured. У source совпадают type, URL и accessedAt. Пути картинок и media sourceId тоже совпадают; геометрия пар сравнения одинакова. Годы изображений должны обозначать одно и то же время, даже если подписи с «около» переводятся.
4. `letter` словарной статьи выбирайте по **английскому** заголовку. Абзацы должны соответствовать русским по смыслу и числу. Не оставляйте русскую прозу в английском content как временную заглушку.
5. Проверьте обе страницы и переключение языка. Новый материал готовьте сразу на двух языках: сейчас обе локали production, и отсутствие пары мешает проверкам/сборке.

## 5. Что можно менять самостоятельно

### Можно самостоятельно

Исправлять явные опечатки и пунктуацию, улучшать формулировку без изменения факта; корректировать alt и обычные подписи после сверки с оригиналом. Сохраняйте ID, slug, даты и связи. Перед передачей проверяйте оба языка. Для Timeline даже простая текстовая правка может потребовать помощи с защитными тестами — это особенность текущего проекта, а не ошибка JSON.

### Нужно внимательно проверять

Новые исторические сведения, новые абзацы, записи, источники, связи, координаты, статусы и изображения. Сначала учитель проверяет смысл и источники; затем разработчик при необходимости согласует новый состав с тестами и подготовкой медиа. Самостоятельно подготовить материал можно, но не обещайте готовую публикацию сразу после сохранения.

### Лучше с помощью разработчика

Изменение или удаление существующих ID/slug, структуры JSON, модели данных, программного кода, подборок главной, Hero, крупных блоков Timeline, каталога доставки картинок и тестовых ожиданий. Также первоначальная настройка компьютера и публикации. Не меняйте `.env`, API-ключи, GitHub Secrets, настройки Actions/Pages и `nuxt.config.ts` для редактирования статьи.

## 6. Как проверить изменения

### Шаг 1. Проверить JSON в редакторе

Сохраните оба языковых файла и откройте **Вид → Проблемы**. Исправьте кавычки, скобки, запятые. Если видите много ошибок, начните с первой: одна потерянная кавычка может вызвать десятки сообщений. Убедитесь, что VS Code распознал файл как **JSON** (справа внизу).

### Шаг 2. Проверить ID и соответствие RU/EN

Через **Ctrl+Shift+F** / **⌘Shift+F** ищите по папке проекта. У каждого нового ID должна быть одна запись в нужном RU-файле и одна в EN; множество упоминаний в связях нормально. В пределах одного каталога ID и slug уникальны. Для связей проверяйте именно существование объекта с `"id": "…"`, а не только встречу слова в тексте.

Сравните язык, число абзацев, одинаковые технические значения и порядок списков связей. Для изображений проверьте файл в `public`, источник и английскую подпись. Не удаляйте историю источников или неподтверждённые поля, лишь бы сделать проверку зелёной.

### Шаг 3. Запустить реальные команды проекта

Откройте **Терминал → Новый терминал** в VS Code. Он должен быть открыт в папке `1812`, где лежит `package.json`. Вводите команды по одной и дождитесь завершения. Проект использует Node **22.23.3** из `.nvmrc`; если окружение ещё не настроено, попросите помочь с ним, не меняйте версию проекта.

| Команда                | Что проверяет / делает                                                                           | Когда нужна                                                                        |
| ---------------------- | ------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------- |
| `npm test`             | Существующие проверки контента, связей, Hero, карты, ссылок, доставки изображений и homepage map | После содержательных изменений; внимательно читать ошибки                          |
| `npm run typecheck`    | Соответствие данных и кода ожидаемым типам                                                       | Перед передачей новых записей и структурных изменений                              |
| `npm run format:check` | Оформление файлов, включая content RU/EN                                                         | Перед передачей; не исправляет файлы                                               |
| `npm run lint`         | Правила программного кода, не историческую достоверность текста                                  | Если руководитель просит техническую проверку; это не отдельный JSON-валидатор     |
| `npm run dev`          | Локальная версия сайта с обновлением после сохранения                                            | Чтобы посмотреть свои изменения                                                    |
| `npm run generate`     | Проверяет конфигурацию и создаёт статические страницы в `.output/public`                         | Финальная проверка согласованного пакета с руководителем, особенно новых маршрутов |

В `package.json` также есть `npm run build`, `npm run preview` и адресные render-проверки: `npm run test:homepage-render`, `test:links-render`, `test:places-detail-render`, `test:timeline-detail-render`, `test:map-index-render`, `test:dictionary-places-render`, `test:stage8-navigation` (для каждой используйте начало `npm run`). Render-проверки читают подготовленные страницы/окружение согласно своему тесту; это не первая команда для проверки одной опечатки. Разработчик выбирает нужную проверку.

Не запускайте `npm run format` вслепую: она переписывает оформление многих папок проекта. Не устанавливайте новые зависимости и не меняйте lockfile ради текста. Техническая проверка не заменяет проверку фактов учителем.

### Важно: корректный JSON всё равно может не пройти тесты

Проверки защищают утверждённую редакционную версию. Сейчас в них есть фиксированные количества записей, 95 абзацев словаря, 60 абзацев Timeline, конкретные связи, media manifests и контрольные суммы. **Timeline content защищён контрольной суммой целиком**, а его metadata — отдельно; даже исправление буквы в абзаце может сделать `npm test` красным. Количество абзацев введения главной зафиксировано как три; у «О проекте» зафиксированы ID разделов и маршруты ссылок.

Если изменили именно эти данные и JSON корректен, не отменяйте обоснованную правку только ради зелёного теста и не удаляйте проверку. Передайте разработчику согласованный текст и сообщение об ошибке. Он проверит, что обновление допустимо, и изменит нужное ожидание. Успешный `npm run generate` отдельно не доказывает, что весь `npm test` прошёл: это разные проверки. Существующий deployment workflow не запускает целиком `npm test`, поэтому редакционные проверки важны **до** передачи к публикации.

### Шаг 4. Посмотреть локальный сайт

Выполните `npm run dev`, затем откройте адрес, который напечатан в терминале. Обычно это `http://127.0.0.1:3000`, но при занятом порте он может отличаться. Оставьте этот терминал работающим; для других команд откройте второй. Остановка сервера — **Ctrl+C**.

Откройте именно изменённую страницу, например `/dictionary/berezina` и `/en/dictionary/berezina`; проверьте заголовок, абзацы, изображения и связи. На маленьком экране или узком окне текст не должен уходить за край. Для места проверьте карточку и переход к статье, а для события — порядок в списке. Если живой карты нет из-за окружения, не пытайтесь менять ключ: попросите руководителя проверить её в настроенном браузере.

При добавлении записей локальное приложение тоже может отказаться запускаться из-за несовпадения RU/EN или неизвестных source IDs: их проверяет `nuxt.config.ts`. Сначала подготовьте оба языка и существующие источники, затем пробуйте запуск снова.

### Шаг 5. Передать к публикации

1. Передайте руководителю список изменённых файлов, краткое объяснение и результат проверок. Для нового изображения приложите файл, сведения о происхождении и правах.
2. Ответственный за репозиторий проверяет пакет и отправляет согласованные изменения в ветку `main` на GitHub. До этого сохранение на вашем компьютере не обновляет production.
3. Существующий `.github/workflows/deploy-pages.yml` автоматически запускается при push в `main`: Node 22.23.3 → `npm ci` (установка по lockfile, включая `nuxt prepare`) → `npm run generate` → проверки production metadata/assets → загрузка статического артефакта → GitHub Pages deployment.
4. После успешного workflow откройте опубликованные RU/EN страницы, обновите их и проверьте результат. Если workflow красный, публикацию нельзя считать успешной; сообщение передайте ответственному.

**Для текста не нужно менять Secrets, API-ключи или настройки deployment.** Локальный `.env` с настройками не отправляют в GitHub и не включают в пакет контента. Новая сборка и успешная публикация обязательны, потому что GitHub Pages обслуживает готовые страницы, а не читает ваши локальные JSON-файлы.

## 7. Чек-лист перед передачей

- [ ] Текст проверен на опечатки, пунктуацию и понятность.

- [ ] JSON сохранён без ошибок кавычек, запятых и скобок.
- [ ] ID и slug уникальны; существующие ключи не изменены случайно.
- [ ] Все ID источников и связанных материалов существуют в нужных каталогах.
- [ ] Русская и английская версии согласованы по смыслу и структуре.
- [ ] Файлы изображений существуют; alt, подписи, авторство, права и источник корректны.

- [ ] Руководитель получил только согласованные материалы; настройки и ключи не включены.
