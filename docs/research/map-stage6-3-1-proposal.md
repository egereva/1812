# Stage 6.3.1 — Interactive Map: UX and architecture proposal

**Status: Stage 6.3.1 COMPLETE — approved with corrections.** Stage 6.1 and 6.2 remain complete. Stage 6.3.2 has not started. This document specifies the reviewed behavior; it changes no production code or historical content.

## Purpose and editorial layers

`/map` and `/en/map` are spatial indexes for all 13 approved Places. The map takes most of the available viewport, with a compact heading, layer switch, map controls, and a contextual Place card. It uses the existing ivory, graphite, burgundy, serif, and thin-rule visual system. The Yandex base map stays legible; project controls and markers carry the museum identity. No permanent sidebar, default balloon, geocoding, or invented historical copy.

The layer is derived from the existing `historicalStatus`, independently of `category` and `locationPrecision`. `All` is the union of both exclusive layers. The complete assignment is:

| Layer  | Existing status     | Place IDs                                                                                                      |
| ------ | ------------------- | -------------------------------------------------------------------------------------------------------------- |
| 1812   | `event-site`        | `fili-village`, `kuntsevo-estate`, `poklonnaya-hill`                                                           |
| 1812   | `surviving-witness` | `intercession-church-fili`                                                                                     |
| 1812   | `lost-site`         | `dorogomilovskaya-gate`, `dorogomilovskoe-cemetery`                                                            |
| Memory | `reconstruction`    | `kutuzov-hut`                                                                                                  |
| Memory | `memorial`          | `brotherhood-grave-obelisk`, `milepost-fili`, `archangel-michael-chapel`, `kutuzov-monument`, `triumphal-arch` |
| Memory | `museum`            | `borodino-panorama-museum`                                                                                     |

Thus **All 13 = 1812 6 + Memory 7** in each locale. The Hut is the 1887 reconstruction, the Church a surviving witness, and Kuntsevo a historical site whose present building is later. The approximate Poklonnaya Hill, lost Gate, and lost Cemetery remain in the 1812 layer with their precision/status caveats. The present obelisk is the 1940 object in Memory, not the physical 1849 memorial. Neither layer claims that its present object existed unchanged in 1812. A test should assert that all 13 IDs are assigned once and that RU/EN assignments agree.

## Markers, controls, and card

Use `YMapMarker` with an accessible HTML button for each marker, built from maintainable HTML/CSS primitives. One restrained color system: graphite outline and ivory fill for 1812, burgundy accent for Memory; shape and inner glyph carry the stronger distinctions. **Initial visual system for review on the real map:** event site = solid circle; surviving witness = square with central dot; lost site = dashed circle; reconstruction = square with open centre; memorial = diamond; museum = double-ring circle. These exact shapes are not an irreversible design contract. `locationPrecision: approximate` adds a thin dotted outer halo and an accessible “approximate area” label; it never moves the coordinate. An on-demand `Обозначения / Legend` control reveals the six shapes and precision halo; the full key does not occupy map space permanently. Default is small but a 44×44 px invisible hit area; hover adds a subtle outline; keyboard focus uses a clearly visible 2 px ring; selected gets a larger burgundy outer ring, higher stacking order, and matching list/card state. Neither color alone nor motion conveys selection; do not add unrelated colors.

The segmented `All | 1812 | Memory` control is compact, keyboard operable, and `aria-pressed`/radio-group semantics describe the active layer. Initial layer is All. Changing layers closes a selected Place that is no longer visible, removes its `place` query, and fits the newly visible markers once; subsequent user panning/zooming is respected until another explicit layer or deep-link action. If the selected Place belongs to the chosen layer, keep it selected and the card open. Map chrome is limited to essential zoom control and required Yandex attribution; the layer switch and index control use project styling.

**Desktop (1440):** a floating, width-constrained Place card sits inside the map frame in an unobtrusive corner, with camera padding so the selected marker is not hidden. It contains the approved `historicalStatus` label, `title`, `shortDescription`, `address` when present, optional `coverImage` with its approved caption/credit/source, a concise `locationNote` for approximate positions or essential `historicalNote` where needed, a direct `Подробнее →` / `Read more →` link to `/places/{slug}`, and at most one useful related Timeline link. There is a visible Close button. No gallery, long article, or generated historical text. The three intentionally imageless Places use the same compact typographic card without an empty image frame.

**Mobile (320/390):** the selected Place opens one polished, content-sized bottom card, capped at roughly 45–50% of the viewport. It has explicit Close and the same concise approved fields as the desktop card; use internal scrolling only if the content genuinely exceeds the cap. The map stays visible and its exposed area retains normal gestures. There is no draggable, expandable, or multi-state sheet in Stage 6.3.2. On tablet (768) use a shorter bottom or side-floating card according to usable map width; at 1440 use the desktop card. Card width, safe-area insets, 44 px controls, and an always visible map area are checked at 320, 390, 768, and 1440.

## URL state and cross-navigation

Public URLs use `slug`, matching existing `/places/{slug}` routing; IDs stay internal relation keys. `/map?place=kutuzov-hut` and `/en/map?place=kutuzov-hut` resolve through `getPlaceBySlug`, select the marker, fit/offset the camera, and open the card after map readiness. The selected card can render from the query in SSR before the map canvas is ready, avoiding a hydration mismatch and keeping the deep link useful without JS. Marker selection uses a shallow router query update, preserving the locale without full navigation; one deliberate selection creates a Back entry, while camera gestures do not. Closing removes `place`; browser Back restores the prior valid selection. Unknown, repeated, or malformed `place` values are ignored with a readable all-places view; they never produce a 404. When a valid deep link targets a Place outside the current layer, switch to its layer before selecting it. Layer state uses `?layer=1812` or `?layer=memory`; absent/invalid values mean All. Avoid unnecessary query combinations and never retain a selected Place hidden by the layer. Camera state stays out of the URL.

Every Place detail page will gain a prominent, visually meaningful `Показать на карте →` / `Show on map →` action immediately after the lead/intro, using `localePath('/map')` plus that record's `slug`. It is a primary contextual map action, not an incidental inline link. The current Place detail is still a technical text preview, so this is a focused insertion, not a redesign. The homepage Map Preview already links to the map and shows three Place names beside an abstract diagram. Keep the composition; strengthen the existing localized CTA and optional section lead so it clearly invites exploration of all 13 Places. The preview remains an abstract diagram, never a second live Yandex instance.

`resolveRelatedContent(locale, 'timeline', event.id).places` already includes direct and reverse relations. The current data has **three events with four Places each**: `borodino`, `council-fili`, and `moscow-abandoned`. In their existing related-Places section, add one contextual `Места события / Посмотреть на карте` action only when relations exist. Proposed URL `?event={timelineSlug}` opens an event-scoped map view: fit and emphasize the four already related markers, list those four by approved title, and leave the Place card closed until one is selected. `place` and `event` should be mutually exclusive in generated links; if both arrive, a valid `place` takes precedence. The event view is a relation filter/emphasis, not an invented historical layer or story mode. This multi-marker behavior is required by current data, so a single arbitrarily chosen Place would be misleading. Dictionary already has direct/reverse Place relations (for example `fili` has six), but its current detail page renders sources only. Add a compact related-Places list with links to Place details when useful; do not add a general Dictionary→Map CTA. An explicit map link can be revisited only for a specific entry where the Place path is demonstrably insufficient.

## Close-marker audit and behavior

Haversine distances from approved coordinates identify `kutuzov-hut` and `milepost-fili` at **exactly the same point**; `fili-village` is about **3 m** from both, the obelisk about **19–22 m**, and the chapel about **32–34 m** away. Panorama Museum and Kutuzov Monument are about **49 m** apart; the wider Fili group spans roughly **145 m**. Do not perturb stored coordinates or use generic numeric clustering. When hit areas overlap at the current zoom, pointer/touch activation fans member markers out locally in screen space around their approved geographic anchor. Fan-out order, radius, and placement are deterministic; geographic coordinates never change. Each exposed marker is individually selectable, and the selected marker remains visually dominant. Collapse the fan-out on Close, map-background interaction, or another selection. At high zoom distinct markers separate naturally; the exact Hut/Milepost pair remains independently reachable through fan-out at every zoom. Keyboard users receive an equivalent named member chooser/list in stable content order, and the 13-place HTML index provides another reliable path to every Place. No third-party clustering/spiderfy dependency. Test at each target viewport and multiple zooms, including exact-coincident deep links.

## Accessibility and resilience

Expose a semantic, SSR-rendered index of all 13 localized Place links adjacent to the map. In the successful-map state, a compact project-styled `Места · 13 / Places · 13` control reveals it in a lightweight panel; it does not compete permanently with the map. On map/API failure, the complete list becomes directly prominent without opening the panel. Its order follows the content catalog; layer and event views may narrow the interactive index but the failure state always offers all 13. Map marker buttons have localized `Place title — historical status — exact/approximate` names. Tab follows deterministic content order; Enter/Space select; Escape closes the card/fan-out/member chooser and restores focus to its invoking marker or list item. Opening the card does not steal focus on pointer input; keyboard activation moves focus to its heading or first action, with a documented return target. An `aria-live` status announces selection/layer/error without reading map tiles. Focus rings remain visible over map colors. Reduced-motion preference disables camera animation and card transitions. Keyboard users can reach the entire collection through the HTML index even if Yandex's own canvas navigation differs by browser.

SSR shows the map frame, loading status, layer controls, and complete HTML index without requiring map JS. Missing key in development, API timeout/load failure, or map initialization error replaces the frame with a plain explanation and the full index; it never removes Place navigation. A no-JS visit remains useful. Images load lazily only when a card is opened; text-only cards need no placeholder. The map page should not load Yandex on Homepage, Timeline, Dictionary, or Place routes.

## Yandex Maps JS API 3.0 / Nuxt 4

`nuxt.config.ts` currently has SSR and static prerender enabled and **does not declare a map key**. In 6.3.2, declare a public runtime config field backed by `NUXT_PUBLIC_YANDEX_MAPS_API_KEY` and read it only in client-side map loading. For static output, the public key must be available at generation time; it is browser-visible and should have HTTP Referer restrictions. No value belongs in source, logs, or this document. Yandex 3.0 loads from its v3 URL with `apikey` and `lang`, and code waits for `ymaps3.ready`; the core map uses `YMap`, `YMapDefaultSchemeLayer`, `YMapDefaultFeaturesLayer`, and custom-DOM `YMapMarker`. API coordinates are `[lon, lat]`, unlike the content object's `{lat, lon}`. `setLocation` supports center/zoom or bounds, and `destroy()` tears down the map on unmount. See the official [connection guide](https://yandex.com/maps-api/docs/js-api/common/connection/javascript.html), [markers guide](https://yandex.com/maps-api/docs/js-api/object/markers/index.html), [YMap API](https://yandex.com/maps-api/docs/js-api/map/YMap.html), and [localization](https://yandex.com/maps-api/docs/js-api/map/localization.html).

Render the frame and text index on the server; mount only the map canvas in `<ClientOnly>` after hydration. A small client-only loader memoizes the script/ready promise per active document, applies a timeout/error path, and creates one map instance per mounted page. Component teardown calls `destroy()` and removes listeners/DOM references, while the script may remain cached for a later visit. Because API `lang` is chosen at script load, map-route language switching should perform a document navigation to the localized route, preserving valid `place`/`event` state; this reloads the base map in `ru_RU` or `en_RU` while keeping kilometer units. Other routes retain normal Nuxt locale switching. Prefer direct API integration over a wrapper or global store. Keep only selected ID, layer, and optional event slug reactive; do not mirror the full camera state into Vue/URL. Keep the base map's necessary attribution visible.

## Reviewed decisions

The exclusive **1812 6 / Memory 7** assignment, including the lost Cemetery in 1812 and present obelisk in Memory, is approved. The event-scoped `?event=` URL is approved; event views emphasize only existing relations and draw no historical route. Pointer/touch overlap resolution uses deterministic screen-space fan-out, with an equivalent named keyboard chooser. Marker shapes remain subject to visual review after the first implementation. The first mobile implementation is one compact bottom card, without draggable or expandable states. The Places index and full legend open on demand, while map failure exposes all 13 Places immediately. No further editorial decision blocks Stage 6.3.2, which has not started.
